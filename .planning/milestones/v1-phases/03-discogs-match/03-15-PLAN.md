## Gap

**Source:** 03-VERIFICATION.md `gaps:` (new CR-01, ROADMAP SC2 / DISC-03, and the 03-07 connect-backfill truth), plus WR-01 from 03-REVIEW.md.

**State at HEAD (planner check, 2026-10-21):** confirmed by reading the code and by a scratch Vitest run against HEAD that uses the harness from reactivated-spine.test.ts. The run used the real handler, the real completeConnect and a stubbed global fetch. Steps:

1. Auto search A ends failed (a 422).
2. The owner presses Retry. A 401 ends the Retry B as auth_failed, with the same input hash as A, and turns Reconnect needed on.
3. completeConnect saves the sign-in and backfills.

Result: s0 still has only `[auto failed, again auth_failed]`, and its card is `{ state: 'failed', failure: { kind: 'auth' } }`. The cause is in enqueue.ts. The `due` precheck and `enqueueAutoSearch` compare against `baselineSearch()`. That function skips the auth_failed row and finds A, which covers the inputs, so both return early.

**Rule chosen: (a), the connect replays the rejected search.** Reasons:

1. **03-07 truth:** "Finishing a connect … backfills a search for every active CD spine … whose latest search ended … auth_failed." Rule (a) makes the code match it. Rule (b) would leave it false.
2. **The app's own copy:** the /spines alert promises "Reconnect your Discogs account in Settings and the CDs here are looked up again." The card line says "Reconnect Discogs in Settings." Both promise a lookup after reconnecting. Rule (b) would show an older result instead of looking anything up.
3. **D-06 (owner intent):** in the reachable path, the rejected search is the owner's own Retry or Search again. Rule (a) completes the action the owner already took. Rule (b) drops it and shows the failure they were retrying.
4. **Fits the read model:** rule (b) needs connection state inside the pure read model, which `effectiveSearch` does not have. Without it, the rejection would be hidden while the app is still disconnected.
5. **Bounded cost:** at most one paced read per rejected spine for each owner action (a connect or a Test connection). The maintenance hook is unchanged (T-03-17).

The trade-off: the 03-07 enqueue test that pinned "no repeat over a done search with the same inputs" is rewritten to the new rule (Task 1 step 5). This reversal is deliberate and is recorded in the SUMMARY.

**Same family, also closed:** the server keeps the "rejected" flag in memory, and a restart clears it. Test connection only backfilled when the flag was set. So after a restart, a passing test did nothing for these spines (Task 2).

**Found while planning:** the first `describe` in `src/app/api/discogs/test/route.test.ts` has no `useTempDataDir()`. Its passing tests already reach `enqueueMissingSearches`, which opens `<cwd>/data/app.db`, the owner's real database. Task 2 widens that path, so Task 2 also gives that describe a temporary DATA_DIR (T-03-49).

No schema change. API coverage: `COVERAGE.md` already holds a decided matrix for the Discogs API, and this plan uses only capabilities it marks INTEGRATE (oauth_access_token, oauth_identity, database_search). Schema gate: no schema files touched.
