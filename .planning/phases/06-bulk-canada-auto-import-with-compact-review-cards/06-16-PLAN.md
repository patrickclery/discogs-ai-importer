<objective>
Close the server half of gap G-06-side-1. Each bulk run records the fallback country. When the Canadian versions answer has no usable version, the resolve_pressing job asks Discogs for the same master's CDs from the fallback country (the D-01 query shape with the other country) and lets choosePressing rank them. Then the live stack is proved against the fake Discogs.

Purpose: Bulk import goes Preferred -> Fallback -> top match, so a master with no Canadian CD gets a US CD instead of whatever country the top match was.
Output: Migration 0005, the run snapshot, the second lookup in the job, and an updated live proof.
</objective>

Request count, a deliberate deviation from the orchestrator's note: the orchestrator asked for "the SAME versions answer (no extra Discogs request)". That is not possible without breaking the main path. D-01's request filters by country (versionsQuery sends country=Canada), so its answer holds no US versions. Dropping the filter returns at most one page of 100 CDs, earliest first, and on a large master that page can miss the Canadian pressing. So the job sends one more GET, in the same D-01 shape with the fallback country, and only when needsFallbackLookup (06-13) says it can change the result. Spines with a Canadian version, spines whose top match is already from the fallback country, spines with no master and runs without a fallback still make one request (or none), exactly as before. Rating: reversible. Changing to a single unfiltered request later is a code-only change.

Run snapshot: the run already snapshots the preferred country and the folder at start (WR-01), so the fallback country goes on bulk_runs too. A later Settings change then never alters a run in progress or its Retry. startBulkRun takes `fallbackCountry` as optional, defaulting to null (no second tier, today's behavior). The eight existing test callers stay as they are, and the route always passes it.
</context>
